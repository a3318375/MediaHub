## 原始检查发现

1. **优先处理前后端版本不匹配。** 前端 `14e1c67` 的资源页先读取 `/api/v1/resources/meta`；本机后端 `083a282` 仅挂载 search，缺 meta/check，导致配置加载失败、搜索按钮禁用。后端 searchRequest 也没有 plugins/channels/mode，cloudTypes 最多 4 项。建议先确认并同步正确后端版本，再决定是否需要改代码。证据：`src/components/resource-search-page.tsx:215`、后端 `internal/httpapi/router.go:85` 与 `internal/pansoubridge/handler.go:15`。
2. **合法 JSON 的坏历史记录会造成页面异常。** `readAllSearchHistory` 只检查是否为数组就断言为业务类型；例如 `[null]` 在读取历史时访问 item.kind 会抛错，对象缺少 keyword 等字段也未过滤。现有“历史损坏”测试仅覆盖非法 JSON。建议补最小运行时校验和对应边界测试。证据：`src/lib/resource-search.ts:70`。
3. **typecheck 命令不能作为有效应用检查。** 根 tsconfig 的 files 为空、应用在 references 中；`tsc --noEmit` 不会自动检查引用项目。`pnpm build` 的 `tsc -b` 当前承担了有效检查。建议单独修正检查脚本，避免 CI 产生虚假的通过信号。证据：`package.json:11`、`tsconfig.json`。
4. **尚未接入的动作容易误解为真实业务。** 动漫订阅由 MSW 返回和修改演示数据，关闭 mock 后后端无对应路由；详情操作可回退到空函数，整理与日历是预览。建议决定是否增加“演示/待接入”提示或暂时禁用无实现动作，保持现有视觉布局。证据：`src/mocks/handlers.ts:52`、`src/components/media-detail-page.tsx:127`、`src/App.tsx`。
5. **正式 API 类型仍依赖 mock。** media-api 引入 mocks 中的 AnimeSubscription、Emby 类型。建议在真实订阅接入时将契约移至 lib，mock 反向引用正式契约，避免演示结构成为接口事实标准。证据：`src/lib/media-api.ts`。
6. **资源页职责集中、缺少交互回归。** 同一组件包含 HTTP、异步收集、合并、缓存、检测和 UI；合并过程中在 setResult updater 中调用 setTab，增加 StrictMode 下副作用推理难度。现有测试没有覆盖该组件的取消、切换搜索和检测流程。建议先补关键交互验收，必要时只抽取 API 与纯合并函数，暂不重构页面。
7. **首包偏大。** build 主 JS 625.31 kB（gzip 201.49 kB），App 静态引入所有页面。可以后续按页面动态加载；属于性能优化，不影响当前设计，优先级低于契约兼容。

## 集成前需要明确的业务边界

- ani-rss 的订阅状态如何映射到本地作品、季度、集数和资源选择，谁持有订阅事实与调度权。
- tgtodriver 的具体项目版本和 API，以及下载、分享转存、磁力离线任务、115 文件操作各由谁执行。
- PanSou 返回的其他网盘链接不天然具备转存到 115 的通路；需要逐类确认可执行动作。
- 下载完成与整理完成应有独立状态；重试、重复资源、重复集数、目标目录冲突及取消操作需要后端规则。
- 作品检索结果不能仅凭标题自动合并跨来源身份；任务应携带明确作品身份与用户确认的资源。

以上是待确认的契约问题，不是已实现能力或本次重构方案。
