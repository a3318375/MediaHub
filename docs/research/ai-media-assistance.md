# AI 辅助识别、整理与订阅需求分析

调研日期：2026-10-15。本文是需求和技术边界设计；未配置模型服务、安装模型、发送私人频道消息，也未产生模型调用费用。

## 优先结论

先把 AI 用作规则识别失败后的补充：提取片名、别名、年份、季集及质量，再从实际查询得到的 TMDB/Bangumi 候选中选择。整理、移动、115 转存、下载状态管理继续由现有公共服务完成。

当前正则能稳定识别的 `S01E02` 不必每次问模型；模型不应直接生成下载链接、猜一个 TMDB ID，或跳过现有整理预览直接移动文件。首次重点应是减少“待识别”，而非增加一个能聊天但无法验证执行结果的入口。

## 已核实的相关实践

- [MoviePilot-Plugins 的 AI 识别增强](https://github.com/liuyuexi1987/MoviePilot-Plugins)：公开说明采用原生识别失败后的结构化 LLM 补充，并交回原生整理流程；也记录失败样本。这与本项目适合采用的边界一致。该项目标示 GPL-3.0，本次只研究方案，没有复制代码；也未对该第三方插件做稳定性保证。
- [Ollama Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)：本地接口可用 JSON Schema 约束输出；当前官方说明云端不支持该项能力，不能把本地能力默认套用于 Ollama Cloud。
- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)：可约束输出结构，但官方明确指出内容仍可能出错；结构正确不等于片名/集数事实正确。
- 云端服务应遵守各自数据政策。以 [OpenAI 数据控制说明](https://developers.openai.com/api/docs/guides/your-data)为例，关闭响应应用状态保存并不自动等于零留存；仍需按接口、组织配置和适用例外核对日志/保留策略。

## 场景优先级

| 优先级 | 需求 | 输入与输出 | 如何验收 |
| --- | --- | --- | --- |
| P0 | 文件名识别补充 | 原始文件名、少量父目录上下文、已知订阅身份 → 片名/年份/季集/质量与证据片段 | 规则成功样本不回退；明确未知时可拒答；ID 由元数据候选验证 |
| P0 | TG 资源块结构化 | 单条消息中的独立资源块 → 多候选及各自的集数/链接关联 | 只能引用输入中已解析的链接 ID；不串联不同作品的标题、体积和链接 |
| P1 | 整理建议 | 识别结果、有限候选元数据 → 已知目录模板和单集映射建议 | 调用现有 Plan/Preview，冲突或多集资源进入待确认；不允许任意系统路径 |
| P1 | 失败样本治理 | 失败原因、人工纠正 → 识别词、别名或正则建议 | 用户可预览规则命中/误命中，再写入规则；保留前后版本 |
| P2 | 自然语言订阅 | “追这部剧、优先 4K、只看某频道” → 订阅草稿 | 明确作品和季数，展示条件，仍调用同一订阅 API |
| P2 | 推荐理由 | 已授权榜单/元数据与用户偏好 → 对候选作品的解释 | 只能推荐实际存在的候选；不编造评分、版权平台或更新日期 |
| 后续 | 海报 OCR/画面识别 | 用户明确提供的图片 → 识别线索 | 比文字识别成本高，先确认文字方案无法覆盖的实际样本 |

## 公共识别能力

建议新增独立 `recognition` 服务，统一给频道监控、PanSou 后处理和整理调用：

```text
文件名/消息块 → 确定性规则解析
   ├─ 作品和季集明确 → 元数据验证
   └─ 缺失或歧义 → 可选 AI 提取 → 元数据受限候选检索
                        → AI 对候选排序 / 无法确认
   → 统一 RecognitionResult → 公共订阅、下载、整理服务
```

建议结果结构：

```json
{
  "title": "候选片名或 null",
  "year": 2026,
  "mediaType": "tv",
  "season": 1,
  "episodes": [2],
  "quality": "2160p",
  "candidateId": "来自本次候选列表的 ID 或 null",
  "resourceLinkIds": ["输入中已经提取的链接 ID"],
  "evidence": [{"field": "episode", "text": "S01E02"}],
  "decision": "matched / ambiguous / unknown",
  "reason": "简短的选择依据"
}
```

缺失字段必须允许 `null/unknown`，不要强迫模型填满。模型自报 confidence 不能直接当真实概率；自动通过条件应来自元数据核验、季集范围、证据和经过样本评估的规则。明确与原始 `S02E03` 冲突的结果必须拒绝。

多季合集、特别篇、上下篇、日期节目、季内/绝对集数转换单独建问题集；初版不把这些全部当普通单集自动归档。

## 供应商与配置

统一业务接口，分别提供适配器，不假定所有“兼容接口”都实现相同 Schema 能力：

| 方案 | 优势 | 需要核对 |
| --- | --- | --- |
| 本地 Ollama | 文件名/频道文本可留在本机，容易做独立服务 | CPU/GPU、上下文、模型许可证、中文季集表现；JSON Schema 能力需实际探测 |
| OpenAI API | 可采用结构化输出和托管模型 | 用户自己的 API 权限、可用地区、账单、数据政策；服务端适配与异常处理 |
| 其他云模型或兼容服务 | 供应商选择灵活 | 不能只测试 `/models` 就认定支持结构化输出；验证具体端点、Schema、超时和错误格式 |

配置项应包含 endpoint、模型名称、加密 API Key、启用场景、每次超时、最大输入/输出、并发、每日预算和是否允许发送私有频道内容。先提供“测试连接与样例识别”，不悄悄使用项目开发者的模型账户。

默认关闭云端 AI；启用时明确实际发送的数据类型和目标。只发送必要文本及经过清理的候选字段，不发送 115 Cookie、Telegram session/API hash、下载提取码、访问令牌或完整库清单。私有频道内容不能因启用公开文件名识别而自动上传。

## 执行和可靠性要求

- 文本、字幕和频道消息都是待分析数据，不能把其中“忽略规则/执行命令/访问链接”当指令。AI 没有直接删除文件、提交下载或访问任意 URL 的工具权限。
- 输出经过 Schema 校验后，还要检查候选 ID、URL 引用、季集范围和目录枚举；只接受当前输入/实际查询得到的资源身份。
- 自定义 endpoint 仅由管理员配置并在服务端使用；本地 Ollama 是明确允许的部署目标，不允许消息文本改变 endpoint。限制重定向和凭证转发。
- 超时、拒答、限流、JSON 错误、候选不足、预算耗尽均返回 `unknown` 或待确认，不中断普通规则路径。
- 缓存键包含输入摘要、规则版本、提示词版本、模型与元数据候选版本。原始私人消息默认不进普通业务日志；保留必要决策摘要，提供清理期限。
- 同一候选仍用公共资源哈希和订阅集数约束去重；AI 不承担任务状态机、重试和资源升级策略。

## 建议实施与评估

第一步：收集脱敏失败样本，做一个没有模型的统一识别结果与证据结构。把当前动漫、电视剧和整理的解析差异记录为测试，不急着统一为一条更宽松的大正则。

第二步：接一个本地/云端可选适配器，仅用于文件名识别补充，输出建议并走现有整理预览。再补频道资源块识别。

第三步：以固定测试集评估：作品准确率、季集准确率、错误自动通过率、可拒答率、增加的成功样本数、平均/尾部延迟、单条和每日费用。至少包括中文别名、拼音、繁简、续季、年份缺失、合集、字幕组标签、多作品 TG 消息及提示注入文本。

初始自动化门槛是设计目标，不是假定已达到的指标：明确错误的自动通过应为零；有歧义宁可待确认。达到目标后才逐步开放自动通过，并保留关闭 AI 后普通订阅与整理照常工作的能力。
