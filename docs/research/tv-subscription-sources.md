# 电视剧订阅：频道监控与 PanSou 两条来源

调研日期：2026-10-15。本文区分已经修改的公共能力与待开发的 Telegram 接入，不代表私有频道现已可用。

后续实现更新：公开 TG 已接入独立读取器，并与 PanSou 互斥选择；补查调度和合集处理以[当前实现说明](../api/tv-subscription-scheduling.md)为准。下文保留调研时的背景与私有账号方案。

## 结论与边界

订阅应按“资源来源”分成两种：`telegram` 为指定频道直接监控，`pansou` 为聚合搜索。两者只负责发现资源，之后共同经过作品匹配、季集识别、链接校验、择优与公共下载，不分别实现 115 转存或磁力离线下载。

当前页面里的 TG 频道设置实际是 **PanSou 的公开频道筛选**，不是已登录 Telegram 的私有频道监控。当前修复已让追剧资源复用公共下载弹窗、文件选择、下载 API 和后端入队服务；自动监控入队仍需下述持久化候选机制。

## Telegram 链接与权限

| 输入 | 含义 | 后端应如何处理 |
| --- | --- | --- |
| `https://t.me/username` / `@username` | 公开用户名；也可能没有网页预览 | 解析成 peer；可用账号直接访问，不把它自动等同于 PanSou 来源 |
| `https://t.me/+hash` / `https://t.me/joinchat/hash` | 私有邀请链接 | 检查邀请；账号需已经加入，或由用户明确完成加入/审核；链接本身不是读取权限 |
| `https://t.me/c/channel/message` | 私有消息定位链接 | 定位已有权限的频道消息，不作为加入邀请 |
| 已保存的频道 ID | 稳定频道身份 | 与已授权账号、access hash 一起解析和保存；不以显示名称作身份 |

Telegram 官方说明了这些[邀请链接](https://core.telegram.org/api/invites)和[消息链接](https://core.telegram.org/api/links)形式。`t.me/瞎写的` 只是占位示例，不应当作实际频道去访问。

历史关键词搜索使用 [`messages.search`](https://core.telegram.org/method/messages.search)，该方法仅供用户账号调用。Bot 可以接收它有成员权限的频道消息，但不能用 Bot Token 任意检索未加入的私有频道历史；参考 [Bots FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get)。

## 正则是否合理

用户提供：

```regex
^(?=.*绿灯军团)(?=.*(?:4K|2160P|UHD))(?=.*2026).*$
```

其实际含义是三个条件同时成立，出现顺序不限：

- 包含“绿灯军团”；
- 包含 `4K`、`2160P`、`UHD` 中任意一个；
- 包含 `2026`。

这作为**单个资源消息块的粗筛规则合理**：频道发帖顺序不统一，AND 条件比写死“片名→年份→画质”顺序更灵活，也便于系统从表单生成。它没有提取集数、链接或体积，更不能证明网盘文件确实是所声称的画质。

局限与原因：

- 默认大小写敏感，`2160p`、`4k` 可能漏掉；应由生成器明确大小写策略。
- `.` 默认不跨换行；频道消息多行时可能漏匹配。可以先把**一个资源块**的空白归一化，或显式开启相应引擎的跨行模式，不能把整条多作品消息拼成一个候选。
- `2026` 是字符串包含判断，也会命中链接数字、发帖日期或其他作品年份；片名可能是别名，续季年份也可能与系列首播年不同。建议把年份做成可选结构化条件，并保存“来自标题还是元数据”的证据。
- 没有季数条件：仅“第 2 集”无法区分 S01/S02。明确季数冲突必须拒绝，未知季数可进入待确认。
- 多个正向前瞻不消费字符，是 AND 条件；`(?:...)` 是非捕获分组，不是提取结果。完整 PCRE 支持并非必要，应避免为了这类规则引入不受控的回溯成本。

当前代码已增加 `textmatch.Compile`：普通 Go 正则照常使用；仅将 `^(?=.*A)(?=.*B).*$` 这类生成式正向组合拆成独立 AND 判断，支持其中的普通嵌套分组和转义，以及显式前缀 `(?i)`。生成式规则匹配前将单个资源块的换行/空白归一化，这是为频道格式做的明确兼容处理，不是逐字复刻 Python 对多行文本的结果。不是完整 PCRE 引擎；负向前瞻、后顾等未支持语法明确报错。原表达式的大小写语义保持不变。

后续表单宜保存 `titles/aliases`、`year?`、`qualityAny`、`includeAll`、`excludeAny`，由后端统一编译，不必强迫用户编辑长正则。高级正则作为补充。

## 建议的数据与处理链

```text
Telegram 已授权频道（历史检索 + 新消息/编辑更新） ─┐
                                                   ├→ ResourceCandidate
PanSou（电影同款搜索，按播出日/每日缺集补查） ──────┘
    → 作品/年份/质量规则 → 单集识别 → 每集择优
    → 持久化待下载候选 → 公共 download.Service
    → 115 分享文件选择/转存或磁力离线 → 公共整理 → 日历回写
```

建议候选包含 `sourceKind/accountId/peerId/messageId/editVersion`、原始消息引用、资源块文本、规范化 URL、提取码、TMDB ID、季集、声明体积、体积来源与匹配理由。来源适配器不得直接调用 115。

Telegram 方案：

1. 用户配置自己的 Telegram API ID/API hash，在本机完成登录及可能的两步验证；会话作为凭证加密落盘，不返回前端、不写日志。默认只读，不发帖、不转发、不自动加入频道。
2. 解析用户选择且账号有权限的频道，保存稳定 peer 身份。首次按作品别名检索历史，设置起始日期/最大回溯量，分页并遵守服务端 `FLOOD_WAIT`。
3. 频道级单例监听，供多个订阅共享。监听新增和编辑消息，处理 URL entities、隐藏 text-url、正文及 caption。以账号+peer+message 身份去重；有消息编辑版本，避免“先发布占位、后补链接”漏检。
4. 使用 Telegram 更新状态恢复断线期间消息；只有消息和候选写入同一事务成功后才推进游标。没有读取权限时明确停用，不能悄悄降级成全网搜。
5. 手动历史补查与实时监听共用解析器。自动渠道优先取单资源块和单集候选；多作品消息、S01E01-E10、合集、季数冲突先进入待确认。

PanSou 方案：

- 保留电影现有的来源设置、并发限制和缓存；增加缺集集合、季数/集数过滤和每集择优，不重做电影下载流程。
- 关键词不宜只用一个中文片名；可由 TMDB 别名生成少量受限查询，结果必须重新核对作品身份。避免每个别名乘每一集造成大量上游请求。
- 首版保持“115 分享优先，其次磁力；同类按体积”。体积未知应标明，不把整季总量当单集体积。后续可用用户选择区分严格过滤与偏好排序。

## 自动下载所需的下一步

当前已接公共**手动**下载。自动模式需明确配置后启用，不能仅发现一个分享就默认转存整份合集：

- 持久化 outbox，以 `subscription + season + episode + canonical resource + rule revision` 保留选择和入队状态；任务创建成功再记录 task ID，崩溃重试交由公共资源哈希去重。
- 分开 `discovered / queued / downloading / completed / failed`，找到资源不等于下载成功或缺集补齐。
- 115 先读分享清单，按文件名确认对应集数；磁力先规范化 infohash。失败资源可切换下一候选；已完成集是否允许更高质量升级由策略控制。
- 入队前复查暂停、规则版本、115 账号及目标目录。下载提交、重试、轮询、日志、整理全部使用公共流程。
- 验收必须覆盖重启、断线、消息编辑、权限撤回、暂停/恢复、换账号、重复链接、多集分享、下载失败和低质量替换。
